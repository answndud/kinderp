# 면접 질문 은행

## 1. 프로젝트 설명

### Q. 이 프로젝트를 한 문장으로 설명해보세요.

> 원장·교사·학부모가 같은 유치원 데이터를 역할에 맞게 처리하면서, 입학 승인·출결 정정·알림 실패·운영 추적을 안전하게 관리하는 다중 테넌트 Spring Boot ERP입니다.

### Q. 왜 유치원 ERP를 선택했나요?

> 익숙한 CRUD보다 서로 다른 역할이 같은 데이터를 공유하는 도메인을 선택하고 싶었습니다. 유치원은 원장·교사·학부모의 권한이 다르고, 입학·출결·알림이 상태와 시간에 따라 바뀌기 때문에 권한, workflow, 동시성, 운영성까지 보여주기 좋았습니다.

### Q. 가장 어려웠던 문제는 무엇인가요?

> 기능 개수보다 “누가 어떤 tenant의 어떤 원생을 언제 어떤 상태로 바꿀 수 있는가”를 닫는 일이 어려웠습니다. 그래서 URL 권한만 두지 않고 service policy, 관계 검증, 상태 전이, audit, 통합 테스트를 함께 설계했습니다.

## 2. Spring·JPA·데이터

### Q. 왜 모놀리식인가요?

> 현재 규모의 핵심 문제는 서비스 간 통신이 아니라 권한과 상태 정합성입니다. 한 transaction과 tenant 경계를 한 애플리케이션 안에서 검증할 수 있어 모놀리식이 적합했습니다. 규모가 커지면 notification delivery와 audit/reporting처럼 비동기·읽기 중심 영역부터 분리하겠습니다.

### Q. JPA 성능 문제를 어떻게 찾았나요?

> 먼저 representative fixture와 query count 테스트를 만들고, 화면 조회에서 반복되는 lazy loading과 중복 fetch를 확인했습니다. Notepad는 22개에서 5개 query로, Dashboard cache hit은 5개에서 0개로 줄였습니다. 개선 후에도 같은 시나리오를 재실행해 수치를 비교했습니다.

### Q. OSIV를 끈 이유는 무엇인가요?

> View나 Controller가 영속성 컨텍스트에 기대어 늦게 데이터를 읽는 것을 막고, service에서 화면에 필요한 DTO를 명확히 만들기 위해서입니다. 그 대신 fetch 범위와 query 설계를 의식해야 하는 trade-off가 있습니다.

### Q. QueryDSL과 Spring Data 기준은 무엇인가요?

> 조건이 단순한 CRUD는 Spring Data 메서드로 두고, 역할·tenant·상태·검색어·기간이 결합되는 운영 조회는 QueryDSL/custom repository로 분리했습니다. 기술을 일괄 적용하기보다 조회 복잡도 기준으로 선택했습니다.

## 3. 보안·권한

### Q. JWT를 cookie에 넣은 이유는요?

> 브라우저 SSR 환경에서 JavaScript가 access token을 직접 읽지 않도록 HTTP-only cookie를 사용했습니다. 대신 cookie 인증의 CSRF 위험을 고려해 XSRF-TOKEN과 요청 헤더 계약을 두고, cookie 속성과 prod 정책을 별도로 검증했습니다.

### Q. JWT만 사용하면 로그아웃이 어려운데요?

> access token은 stateless 특성상 즉시 철회하기 어렵기 때문에 refresh token을 Redis TTL로 관리하고 active session registry로 revoke 대상을 추적했습니다. 완전한 토큰 블랙리스트의 비용과 세션 통제력 사이에서 refresh/session 중심으로 절충했습니다.

### Q. tenant 격리는 어떻게 보장하나요?

> `SecurityConfig`의 endpoint 역할, `@PreAuthorize`, `AccessPolicyService`의 대상 관계 검증, repository의 kindergarten 조건, 교차 tenant 통합 테스트를 함께 사용합니다. 단순히 URL ID만 믿지 않습니다.

### Q. rate limit의 기준은 무엇인가요?

> 로그인은 IP와 이메일을 함께 보고, refresh와 signup은 IP 중심으로 봅니다. Redis TTL counter로 짧은 시간 창을 관리하며 prod에서 잘못된 limit 설정은 startup validation에서 차단합니다.

## 4. Workflow·Outbox

### Q. 입학 신청을 단순 status update로 만들지 않은 이유는요?

> 상태 전이마다 허용 역할, 다음 상태, 알림, audit side effect가 다르기 때문입니다. review/admission/notification/audit service를 분리해 상태 규칙과 부가 동작을 각각 테스트할 수 있게 했습니다.

### Q. Outbox가 필요한 이유는요?

> DB 저장과 외부 email/push/webhook 전달을 한 transaction에 묶으면 provider 장애가 핵심 업무를 실패시킵니다. 먼저 outbox를 저장하고 worker가 전달하므로 업무 성공과 외부 전달 재시도를 분리할 수 있습니다.

### Q. 실패 알림은 어떻게 운영자가 처리하나요?

> retry/backoff로 일시 장애를 재시도하고, 한도를 넘으면 dead-letter로 격리합니다. 원장 전용 화면에서 timeline을 status·channel·검색어로 좁히고 실패 사유를 본 다음 명시적으로 retry합니다.

### Q. 중복 요청은 어떻게 막나요?

> 출결 변경 요청은 requester별 idempotency key를 저장하고 DB unique 제약을 둡니다. 재시도된 같은 요청은 기존 결과를 재사용하거나 중복으로 거절합니다. 상태 전이도 현재 상태를 transaction 안에서 다시 확인합니다.

## 5. 운영·품질

### Q. 실제 배포했나요?

> 실제 클라우드 운영은 아직 하지 않았습니다. 대신 Docker·prod compose·환경 계약·readiness·배포 SHA·backup/restore·rollback script와 fail-closed startup validator를 준비했고, 외부 HTTPS·운영 DB 연결 후 남은 검증 항목을 문서로 분리했습니다.

### Q. 테스트를 많이 작성했는데 어떻게 유지했나요?

> 모든 코드를 같은 수준으로 무겁게 검증하지 않았습니다. Controller·보안·workflow·tenant 경계는 통합 테스트를 우선했고, 순수 규칙은 단위 테스트, 대표 화면은 performance smoke와 browser smoke로 분리했습니다. push에는 빠른 CI, 필요할 때 heavy workflow를 실행합니다.

### Q. AI로 만든 코드 아닌가요?

> AI는 요구사항 분해, 설계 후보 비교, 누락 점검에 활용했습니다. 하지만 실제 반영 여부는 저장소 규칙, 컴파일·테스트·query 수치·보안 계약을 기준으로 직접 판단했습니다. 설명할 수 없는 코드는 채택하지 않는 원칙을 두었습니다.

### Q. 가장 아쉬운 점은요?

> 실제 외부 provider와 클라우드 환경에서 p95·복구·rollback을 확인하지 못한 점입니다. 다음 단계는 비용이 통제된 staging에서 HTTPS, 운영 MySQL/Redis, provider sandbox를 연결하고 같은 runbook을 실행하는 것입니다.

## 6. 답변 공식

