# 기술 질문 심화 은행

프로젝트 설명을 넘어 Java·Spring·JPA·SQL·Redis·HTTP·테스트 기본기 질문을 준비하는 문서입니다. 답변은 `정의 → 이 프로젝트의 선택 → 근거 → 검증 → trade-off` 순서로 말합니다.

## Java 기본기

### Q1. `equals()`와 `hashCode()` 계약은 무엇인가요?

논리적으로 같은 객체라면 같은 hash code를 가져야 합니다. hash code가 같다고 반드시 같은 객체는 아니며, HashMap은 hash bucket 이후 equals를 확인합니다. mutable field를 key equality에 넣으면 저장 후 조회 위치가 달라질 수 있습니다. 이 프로젝트에서는 DTO/식별자와 JPA entity identity를 구분합니다.

### Q2. `record`와 JPA entity를 왜 구분하나요?

record는 불변 값과 API 계약에 적합하고 구성 요소 기반 equality를 제공합니다. JPA entity는 persistence context, dirty checking, 식별자 lifecycle을 가지는 변경 객체입니다. request/response DTO와 entity를 외부 계약에서 구분한 이유가 여기에 있습니다.

### Q3. `Optional`을 어디에 사용하나요?

조회 결과가 없을 수 있다는 사실을 repository/application 경계에서 표현하고 service에서 `orElseThrow`로 도메인 예외를 만듭니다. entity field나 모든 parameter에 Optional을 넣거나 `get()`으로 실패를 숨기지는 않습니다.

### Q4. checked·unchecked exception과 transaction rollback 관계는요?

checked exception은 호출자가 처리·선언해야 하고 unchecked exception은 RuntimeException 계열입니다. Spring transaction 기본 rollback은 unchecked 중심이므로 외부 checked exception을 domain exception으로 변환할 때 rollback 정책을 확인합니다. 이 프로젝트는 `BusinessException(ErrorCode)`로 API 계약을 통일합니다.

### Q5. 불변 객체가 동시성에 유리한 이유는요?

생성 후 상태가 바뀌지 않아 공유 race가 줄고 결과를 추론하기 쉽습니다. 다만 JPA entity는 transaction 안에서 변경되므로 DTO·cursor·payload와 aggregate를 구분합니다.

## Spring 핵심

### Q6. IoC와 DI는 무엇인가요?

IoC는 객체 생명주기와 의존성 연결의 제어권을 container가 갖는 것이고, DI는 필요한 의존성을 주입하는 방식입니다. 생성자 주입은 필수 의존성을 드러내고 테스트 대체가 쉽습니다.

### Q7. singleton bean에 request 상태를 field로 두면 왜 안 되나요?

여러 요청 thread가 같은 bean을 공유하므로 mutable request 상태가 섞입니다. 요청별 값은 parameter나 local variable로 관리하고 service field에는 repository·설정 같은 공유 의존성만 둡니다.

### Q8. `@Transactional`은 어떻게 동작하나요?

Spring AOP proxy가 method 전후 transaction을 시작·commit·rollback합니다. self-invocation은 proxy를 통과하지 않아 annotation 기대와 다를 수 있습니다. 이 프로젝트는 service operation을 transaction 경계로 두고 외부 HTTP 호출을 긴 transaction에 넣지 않습니다.

### Q9. `readOnly=true`가 쓰기를 절대 막나요?

아닙니다. DB/provider에 따라 최적화 힌트이며 보안 장치가 아닙니다. 쓰기 방지는 service 설계·권한·DB 제약으로 보장합니다.

### Q10. Filter·Interceptor·ControllerAdvice의 차이는요?

Filter는 servlet/Security chain 앞단, Interceptor는 MVC handler 전후, ControllerAdvice는 Controller 예외·응답 공통 처리에 적합합니다. JWT/CSP는 filter, 역할별 redirect는 interceptor, API 오류 포맷은 advice에 배치했습니다.

### Q11. 401과 403은 어떻게 구분하나요?

401은 인증되지 않았거나 인증이 유효하지 않은 경우이고 403은 인증됐지만 권한이 없는 경우입니다. Security handler는 Controller 전에 실행될 수 있으므로 두 계약을 HTTP 테스트로 따로 검증합니다.

### Q12. Spring profile을 왜 분리하나요?

demo의 seed·Swagger·app-port Prometheus와 prod의 안전 기본값이 다르기 때문입니다. `StartupSafetyValidator`로 prod에서 seed·Swagger·약한 secret·비HTTPS CORS가 켜지지 않게 합니다.

## JPA·transaction

### Q13. N+1 문제는 무엇이고 어떻게 찾았나요?

목록 하나를 읽은 뒤 각 row의 연관 데이터를 별도 query로 읽는 문제입니다. SQL 로그와 Hibernate query count로 확인하고 projection/fetch 범위/batch fetch 중 하나를 선택합니다. Notepad query count를 22에서 5로 줄인 것이 대표 사례입니다.

### Q14. fetch join과 pagination을 함께 쓸 때 주의점은요?

collection fetch join은 row 중복·메모리 pagination·count query 문제를 만들 수 있습니다. ID/page와 상세 조회를 나누거나 DTO projection을 사용하며, fetch join 하나로 모든 N+1을 해결한다고 가정하지 않습니다.

### Q15. 영속성 컨텍스트와 dirty checking은요?

transaction 안에서 관리되는 entity 변경을 commit 시점에 감지해 update합니다. bulk update와 섞으면 context가 오래된 값을 가질 수 있어 clear/조회 경계를 확인합니다.

### Q16. optimistic·pessimistic lock 선택 기준은요?

충돌이 드물고 재시도가 가능하면 optimistic version, 짧은 자원 경쟁에서 초과 배정을 반드시 막아야 하면 pessimistic row lock을 검토합니다. Outbox claim은 `FOR UPDATE SKIP LOCKED`로 worker 경쟁을 줄입니다.

### Q17. isolation level을 설명해보세요.

read uncommitted, read committed, repeatable read, serializable은 dirty/non-repeatable/phantom read와 동시성 비용이 다릅니다. annotation 하나로 해결한다고 하지 않고 실제 불변식·DB isolation·lock query를 함께 확인해야 합니다.

### Q18. soft delete의 문제는요?

조회마다 deletedAt 조건을 빠뜨리면 삭제 데이터가 재노출됩니다. unique 제약·연관 관계·복구 정책도 복잡해지므로 repository/query와 접근 테스트에서 일관되게 적용합니다.

## SQL·MySQL

### Q19. 복합 인덱스 순서는 어떻게 정하나요?

실제 where equality/filter, range, order by와 selectivity를 보고 정합니다. 대표 query의 EXPLAIN 없이 모든 컬럼을 인덱스에 넣지 않습니다. Outbox dead-letter 최신순 조회는 status·channel·dead_lettered_at·id 패턴에 맞췄습니다.

### Q20. 인덱스가 항상 빠른가요?

아닙니다. low selectivity, 작은 테이블, leading wildcard, 잘못된 통계에서는 scan이 더 나을 수 있습니다. 쓰기 비용과 저장 공간도 증가하므로 실행계획으로 검증합니다.

### Q21. unique 제약을 애플리케이션 검사만으로 대체하면 안 되는 이유는요?

동시 요청이 같은 exists 결과를 보고 동시에 insert할 수 있기 때문입니다. 최종 불변식은 DB unique constraint가 보장하고 service는 충돌을 사용자 오류로 변환합니다. 출결 idempotency key가 사례입니다.

### Q22. offset pagination의 한계는요?

뒤 페이지로 갈수록 건너뛰는 비용이 커지고 중간 삽입·삭제 때 중복·누락이 생길 수 있습니다. 대규모 feed가 되면 정렬 키가 포함된 keyset/cursor로 전환합니다.

## Redis·Outbox

### Q23. Redis cache invalidation은 어떻게 하나요?

cache key·TTL·무효화 대상을 명확히 하고 MySQL을 source of truth로 둡니다. 이 프로젝트의 dashboard cache는 보조 cache라 hit 수치가 운영 데이터 정합성보다 우선하지 않습니다.

### Q24. Outbox와 메모리 비동기 thread의 차이는요?

메모리 queue는 프로세스가 죽으면 작업이 사라질 수 있지만 DB Outbox는 업무 transaction과 함께 영속화됩니다. 대신 claim·stale reclaim·중복 전달·보관 정책을 운영해야 합니다.

### Q25. `SKIP LOCKED`의 trade-off는요?

잠긴 row를 기다리지 않고 건너뛰어 병렬 worker를 돕지만, 현재 batch에서 빠진 작업은 다음 claim이 처리합니다. processing timeout과 reclaim이 필요하며 exactly-once 전달을 자동 보장하지 않습니다.

## HTTP·API·브라우저

### Q26. cookie JWT에서 CSRF는 어떻게 방어하나요?

cookie는 브라우저가 자동 전송하므로 별도 XSRF token을 요청 header로 보내게 하고 서버에서 cookie/header 계약을 확인합니다. credentialed CORS에서 wildcard origin/header를 허용하지 않습니다.

### Q27. HTTP method 멱등성과 업무 멱등성은 같은가요?

PUT/DELETE의 HTTP 의미와 실제 command의 중복 효과는 별개입니다. POST 출결 변경 요청은 `Idempotency-Key`를 받아 DB에 저장해야 재시도 효과를 통제할 수 있습니다.

### Q28. API versioning은 어떻게 관리하나요?

`/api/v1/**` 계약을 유지하고 extension over modification을 우선합니다. 응답 DTO·ErrorCode·ApiResponse를 변경하면 frontend·integration test·문서를 같이 갱신합니다.

## 테스트·운영

### Q29. 단위 테스트와 통합 테스트 기준은요?

순수 상태 전이·계산은 단위 테스트, DB·Security·tenant·migration·controller 계약은 통합 테스트로 둡니다. Controller와 보안 변경은 성공·실패 HTTP 경계를 우선 검증합니다.

### Q30. Testcontainers의 장점과 한계는요?

실제 MySQL·Redis에 가까운 dialect·migration·query를 검증할 수 있지만 컨테이너 시작 비용과 Docker 의존성이 있습니다. 그래서 fast test와 integration test를 분리합니다.

### Q31. 로그에 무엇을 남기고 무엇을 빼나요?

trace id, method, path, status, duration, domain id처럼 장애 조사에 필요한 최소 정보만 남깁니다. 비밀번호·token·민감 body·불필요한 query string은 남기지 않고 내부 exception은 안전한 사용자 메시지로 변환합니다.

### Q32. 실제 배포가 없는데 운영성을 어떻게 주장하나요?

실제 운영이라고 주장하지 않습니다. local/CI/production-like에서 readiness, startup safety, backup/restore, deploy SHA, rollback 자산을 검증했고, 실제 HTTPS·운영 DB·provider sandbox가 필요한 범위를 분리했다고 답합니다.
