# 면접 답변 스크립트

## 1. 30초 자기소개

> 저는 Java와 Spring Boot로 업무 규칙을 API와 데이터 모델로 구조화하고, 권한·성능·운영 실패까지 검증하는 백엔드 개발자 지망생입니다. KinderP에서는 원장·교사·학부모의 tenant 경계, JWT cookie와 Redis 세션 철회, 입학 상태 workflow, 출결 멱등성, 알림 Outbox dead-letter, 감사 로그를 구현했습니다. AI는 문제 분해와 누락 점검에 활용했지만, 설계 선택과 실행·검증 결과는 직접 책임졌습니다.

## 2. 3분 프로젝트 설명

> 이 프로젝트는 유치원 운영 관리 시스템이지만, 핵심은 화면 수가 아닙니다. 원장·교사·학부모가 같은 유치원 데이터를 보면서 가능한 행동이 다르기 때문에 role과 tenant 경계를 먼저 정의했습니다.
>
> 첫 번째 축은 보안입니다. JWT를 HTTP-only cookie로 전달하고 refresh token과 active session을 Redis TTL로 관리했습니다. endpoint의 URL 권한만 믿지 않고 service의 대상 유치원·원생·반 관계를 다시 검증했습니다.
>
> 두 번째 축은 workflow입니다. 입학 신청은 pending, waitlist, offer, approval 같은 상태 전이를 갖고, 상태 변경은 알림과 업무 감사 로그로 이어집니다. 학부모 출결 변경 요청은 별도 큐에서 교사나 원장이 승인해야 하며, requester별 멱등 키로 중복 반영을 막았습니다.
>
> 세 번째 축은 운영성입니다. 알림을 외부 provider와 바로 묶지 않고 Outbox로 분리했습니다. worker가 채널별 adapter를 호출하고, 실패는 backoff·retry 후 dead-letter로 격리합니다. 원장 화면에서 상태·채널·검색어로 실패를 찾고 다시 처리할 수 있습니다.
>
> 성능과 품질은 숫자로 확인했습니다. Notepad query count는 22에서 5로, Dashboard cache hit은 5에서 0으로 줄였습니다. CI는 push용 quick check와 수동 heavy check를 분리했습니다. 실제 클라우드 운영과 외부 provider sandbox는 아직 남았지만, 그 범위를 숨기지 않고 배포 전 안전장치와 다음 검증 절차까지 문서화했습니다.

## 3. AI 활용 답변

> AI를 코드 자동 생성기로만 사용하지 않았습니다. 먼저 요구사항을 role/tenant, 상태 전이, 외부 실패, 감사, 성능 문제로 분해하는 데 사용했고, 그 다음 설계 후보의 누락을 찾는 데 사용했습니다. 제안은 반드시 실제 코드와 테스트로 확인했습니다. 특히 보안·권한은 성공 케이스뿐 아니라 교차 tenant와 잘못된 역할의 실패 케이스를 확인했고, 성능은 개선 전후 query count를 비교했습니다.

## 4. 실패 경험 답변

> 초기에 화면 기능을 늘리는 방향으로 가면 CRUD가 많아지지만, 면접에서 설명할 핵심 문제는 약해진다는 판단을 했습니다. 그래서 기능을 더 추가하기보다 입학 workflow, Outbox 운영, audit, tenant 경계를 분리해 대표 흐름을 닫았습니다. 그 결과 구현 범위는 통제했지만, 실제 provider와 클라우드 운영 증거는 남았고 이를 다음 단계로 명확히 분리했습니다.

## 5. 마지막 요약

> 이 프로젝트에서 보여드리고 싶은 것은 기능을 많이 만들었다는 사실보다, 복잡한 업무를 상태·권한·transaction으로 분해하고 실패를 관측·재시도할 수 있게 만든 뒤 숫자와 테스트로 검증하는 개발 방식입니다.
