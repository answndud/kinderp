# 성능·보안·운영 증거

## 1. 성능 개선 루프

이 프로젝트의 성능 설명은 “빠르게 만들었다”가 아니라 `재현 → 개선 전 측정 → 변경 → 동일 조건 재측정 → trade-off 기록` 순서입니다.

| 대상 | 개선 전 | 개선 후 | 의미 |
| --- | ---: | ---: | --- |
| Notepad 조회 | 22 queries | 5 queries | 조회 DTO와 fetch 범위를 정리해 N+1 감소 |
| Dashboard cache hit | 5 queries | 0 queries | Redis cache hit 시 DB 접근 제거 |
| Dashboard 대표 조회 | 13 queries | 5 queries | 역할별 summary API와 query 재사용 |
| CI 대표 quick check | 5분 28초 수준 | 1분대 대표 실행 | push 피드백 속도 개선, heavy 검증은 분리 |

수치는 local fixture와 제한된 smoke 조건의 결과이며 실제 운영 p95나 대규모 MySQL 실행계획을 의미하지 않습니다.

## 2. 성능 설계 포인트

- QueryDSL은 동적 검색과 운영 필터가 있는 조회에 사용합니다.
- 단순 조회는 Spring Data 메서드명으로 유지해 복잡도를 억제합니다.
- OSIV를 끄고 Controller에서 lazy loading에 의존하지 않습니다.
- `default_batch_fetch_size=100`을 기본값으로 두되, 모든 문제를 batch size로 덮지 않습니다.
- 대시보드에는 역할별 summary API와 Redis cache를 적용했습니다.
- Outbox·audit·notepad는 실제 필터와 정렬 패턴에 맞춰 인덱스를 추가했습니다.

## 3. 보안 방어선

| 위험 | 방어 |
| --- | --- |
| JWT 탈취 후 장기 사용 | HTTP-only cookie, refresh TTL, active session revoke |
| 로그인 무차별 대입 | IP·이메일 기준 auth rate limit |
| CSRF | XSRF-TOKEN cookie와 요청 헤더 계약 |
| IDOR·교차 tenant 조회 | 역할 + tenant + 원생/반 관계 정책 |
| CSP 우회 | inline handler 제거, Content-Security-Policy 적용 |
| 운영면 노출 | prod에서 Swagger·app-port Prometheus·seed 기본 비활성화 |
| 약한 설정 배포 | `StartupSafetyValidator` fail-closed 검사 |
| 내부 오류 노출 | 사용자에는 안전한 메시지, 상세 stack trace는 서버 로그 |
| 삭제 데이터 재노출 | soft delete 조건과 repository 조회 규칙 |

## 4. 운영 자산

- `/actuator/health/readiness`와 `/actuator/info`로 준비 상태·배포 SHA를 확인합니다.
- Docker Compose와 production compose config를 분리합니다.
- 배포 workflow는 SSH known_hosts와 commit SHA를 고정합니다.
- 백업 생성·checksum 검증·복구·데이터 assertion 스크립트를 제공합니다.
- 실패한 알림은 Outbox 운영 화면에서 상태·채널·검색어로 찾고 retry합니다.
- 인증 감사 로그와 업무 감사 로그를 별도 보존·검색합니다.
- graceful shutdown, 로그 보관, backup 경로 안전 가드를 적용했습니다.

## 5. CI 검증 전략

### Push마다 실행하는 빠른 검증

- backend `fastTest`
- frontend asset build
- `bootJar`
- compose config
- 템플릿 접근성·inline handler·product time·view error 검사

### 수동 또는 큰 변경 때 실행하는 검증

- integration test
- performance smoke
- Testcontainers 기반 DB/Redis 시나리오
- 브라우저 smoke

혼자 개발하는 프로젝트에서는 모든 push에 무거운 검증을 강제하기보다, 빠른 실패 신호와 필요 시 깊은 검증을 분리하는 것이 피드백 속도와 신뢰도의 균형에 맞습니다.

## 6. 아직 외부에서 확인하지 못한 것

다음은 구현 부족이 아니라 외부 환경 미연결로 남은 검증입니다.

- 실제 HTTPS 배포 URL smoke
- 운영 DB/Redis의 backup·restore
- 운영 환경 rollback과 `/actuator/info` SHA 대조
- 외부 email/push/app provider sandbox 전달
- 실제 incident webhook 수신
- 실제 트래픽 규모의 k6 p95 및 MySQL 실행계획

면접에서는 이 한계를 숨기지 않고 “로컬 및 production-like 범위에서 검증한 것”과 “외부 연결 후 검증할 것”을 분리해 답합니다.
