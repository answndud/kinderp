# 성능 측정 재현 절차

## 1. 측정 전제

Java 21, Docker MySQL 8/Redis 7, `demo` profile, local fixture 기준입니다. 운영 p95·처리량·SLA로 표현하지 않습니다.

## 2. Query count 재현

```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home
./gradlew performanceSmokeTest --no-daemon
```

대표 테스트는 `NotepadPerformanceStoryTest`, `DashboardPerformanceStoryTest`, `NotificationOutboxPerformanceSmokeTest`, `AuditConsolePerformanceSmokeTest`입니다. fixture 건수, page size, 검색 조건, 개선 전후 query count와 elapsed time, cache miss/hit을 함께 기록합니다.

## 3. HTTP 부하 재현

스크립트는 [`scripts/performance/k6-auth-notepad-dashboard.js`](../../scripts/performance/k6-auth-notepad-dashboard.js)입니다. 실행 전 스크립트가 요구하는 환경 변수와 image tag를 확인하고, 결과에는 VU 수·duration·request 수·error rate·p95/p99·endpoint별 Trend를 함께 남깁니다.

```bash
docker run --rm --network host \
  -e BASE_URL=http://localhost:8080 \
  -e PRINCIPAL_EMAIL=principal@test.com \
  -e PRINCIPAL_PASSWORD=test1234! \
  -v "$PWD/scripts/performance:/scripts" \
  grafana/k6 run /scripts/k6-auth-notepad-dashboard.js
```

## 4. SQL 실행계획

```sql
EXPLAIN
SELECT *
FROM notification_outbox
WHERE status = 'DEAD_LETTER'
  AND channel = 'EMAIL'
ORDER BY dead_lettered_at DESC, id DESC;
```

선택 인덱스, rows estimate, filesort, backward index scan, `LIKE` 검색 추가 시 변화를 비교합니다.

## 5. 해석 규칙

- query count 감소가 항상 latency 감소를 의미하지는 않습니다.
- local Docker CPU·network·buffer pool은 운영과 다릅니다.
- cache hit 0 query는 동일 key와 TTL 조건에서만 성립합니다.
- k6 p95는 애플리케이션·DB·Docker network가 합쳐진 값입니다.
- fixture가 현실을 대표하는지 먼저 확인합니다.

## 6. 현재 결과와 다음 측정

Dashboard 13→5 queries, Notepad 22→5 queries, Dashboard cache hit 5→0 queries, local k6 p95 362.13ms를 관측했습니다. 이는 개선 루프의 증거이지 운영 SLA가 아닙니다. 다음에는 실제 HTTPS에서 DB CPU·connection pool·TLS 네트워크 비용을 같은 시나리오로 측정합니다.
