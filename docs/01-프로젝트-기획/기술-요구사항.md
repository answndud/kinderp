# 기술 요구사항과 완료 기준

## 1. 기술 기준

| 영역 | 선택 | 선택 이유 |
| --- | --- | --- |
| 언어 | Java 21 | record, 최신 JVM 지원, 타입 안정성 |
| 서버 | Spring Boot 3.5.14 | Security·Data·Actuator 생태계와 빠른 운영 검증 |
| 저장소 | MySQL 8 + JPA/QueryDSL | 업무 데이터의 트랜잭션과 동적 조회 대응 |
| 캐시·세션 | Redis | refresh token TTL, active session revoke, dashboard cache, rate limit |
| 인증 | Spring Security + JWT HTTP-only cookie | 브라우저 기반 SSR에서 토큰 노출 면적 축소 |
| 화면 | Thymeleaf + HTMX + Alpine.js | 서버 렌더링을 유지하면서 부분 갱신과 작은 상태 관리 |
| 스타일 | Tailwind 로컬 빌드 | CDN 런타임 의존성 제거와 재현 가능한 asset 생성 |
| DB 변경 | Flyway | 스키마 변경 순서와 배포 추적성 확보 |
| 실행 | Docker Compose | MySQL·Redis 로컬 재현과 production-like 점검 |

## 2. 기능 완료 기준

새 기능은 다음 조건을 만족해야 합니다.

1. API URL 권한과 service의 대상 자원 권한이 함께 검증된다.
2. 입력 경계에 Bean Validation을 적용한다.
3. 비즈니스 오류가 공통 `ApiResponse`·`ErrorCode` 계약을 지킨다.
4. 쓰기 transaction과 읽기 transaction을 구분한다.
5. tenant 조건이 repository/query에 반영된다.
6. 상태 전이가 있는 기능은 성공·실패·중복·권한 실패를 검증한다.
7. 운영에 영향을 주는 schema 변경은 Flyway migration과 복구 전략을 함께 기록한다.

## 3. 품질 예산

- N+1은 로그 또는 query count로 확인합니다.
- 대표 페이지의 query count는 성능 테스트에 고정합니다.
- local/demo/prod의 안전한 기본값을 분리합니다.
- prod에서는 seed·Swagger·app-port Prometheus·약한 secret·비HTTPS CORS를 fail-closed로 차단합니다.
- 템플릿의 label/ARIA/button type/alt와 inline handler를 자동 검사합니다.
- 전체 테스트를 매번 강제하지 않고, 빠른 CI와 수동 heavy workflow를 분리합니다.

## 4. 완료되지 않은 외부 조건

다음은 코드 품질과 별개로 외부 자격증명이 필요합니다.

- 실제 HTTPS 도메인과 TLS
- 운영 MySQL·Redis
- OAuth provider redirect URI와 client secret
- 외부 알림 provider sandbox 및 incident webhook 수신 채널

따라서 문서와 면접에서 “배포 완료”가 아니라 “배포 전 안전장치와 production-like 검증 자산 준비”라고 표현합니다.
