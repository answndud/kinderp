# 제품 요구사항: 유치원 운영 데이터의 안전한 협업

## 1. 제품 한 문장

KinderP는 원장·교사·학부모가 같은 유치원 데이터를 역할에 맞게 처리하면서, 입학 승인·출결 정정·알림 실패·운영 추적 문제를 한 시스템에서 관리하는 내부 운영 플랫폼입니다.

## 2. 문제 정의

유치원 운영은 단순한 원생 CRUD가 아닙니다.

- 원장·교사·학부모가 같은 원생을 서로 다른 목적으로 조회합니다.
- 학부모의 출결 변경 요청은 교사 또는 원장의 검토가 필요합니다.
- 입학 신청은 접수, 대기, 제안, 승인처럼 시간이 지나며 상태가 바뀝니다.
- 알림은 화면에 기록하는 것과 외부 채널로 전달하는 것이 다릅니다.
- 누가 어떤 신청·출결·계정 상태를 바꿨는지 나중에 조사해야 합니다.

따라서 핵심 성공 기준은 화면 수가 아니라 다음 네 가지입니다.

1. 다른 유치원의 데이터가 보이지 않는다.
2. 허용되지 않은 상태 전이가 저장되지 않는다.
3. 외부 전달 실패를 잃지 않고 재시도할 수 있다.
4. 운영자가 문제의 원인과 변경자를 추적할 수 있다.

## 3. 사용자와 권한

| 사용자 | 핵심 책임 | 대표 기능 |
| --- | --- | --- |
| 원장 `PRINCIPAL` | 유치원 운영과 승인 | 대시보드, 반·원생·교사 관리, 입학 승인, Outbox 운영, 감사 로그 |
| 교사 `TEACHER` | 반과 원생의 일상 운영 | 출결, 출결 요청 검토, 알림장, 공지, 반 일정 |
| 학부모 `PARENT` | 자녀 정보 확인과 요청 | 알림장·출결·공지 조회, 입학 신청, 출결 변경 요청, 알림센터 |

권한은 역할 하나만 보는 것이 아니라 `역할 + 소속 유치원 + 대상 원생/반 관계`의 조합으로 판정합니다.

## 4. 핵심 업무 흐름

### 입학 신청

학부모가 신청하면 원장·교사가 검토하고, 대기열 등록·입학 제안·승인·거절로 이어집니다. 상태 변경마다 알림과 업무 감사 로그가 연결됩니다.

### 출결 정정

학부모가 출결 변경을 요청하면 요청은 별도 큐에 쌓입니다. 교사 또는 원장이 승인·거절하고, 승인된 경우에만 실제 출결이 변경됩니다. 동일 요청의 재전송은 멱등 키로 중복 처리를 막습니다.

### 알림 전달

업무 트랜잭션은 알림 provider의 응답을 기다리지 않고 Outbox를 기록합니다. Worker가 채널별 sender를 통해 전달하며 실패하면 backoff·retry 후 dead-letter로 격리합니다.

### 운영 조사

인증 감사 로그와 업무 감사 로그를 분리합니다. 인증 로그는 로그인·refresh·social link/unlink 이상을, 업무 로그는 입학·출결 등 도메인 변경을 설명합니다.

## 5. 범위 밖의 것

- 실제 유치원 고객 데이터를 다루는 상용 서비스라고 주장하지 않습니다.
- 결제·급식·차량 운행·회계 기능은 현재 범위가 아닙니다.
- 실제 외부 알림 provider 운영 계정과 클라우드 배포는 아직 연결 전입니다.

이 범위 통제가 중요한 이유는 포트폴리오에서 기능을 무작정 늘리는 것보다, 선택한 문제를 끝까지 설계·검증하는 능력을 보여주기 위해서입니다.
