# 상태 전이·권한·동시성 설계

## 1. 입학 신청 상태

```text
PENDING ──→ WAITLISTED ──→ OFFERED ──→ APPROVED
   │            │             │
   └────────────┴─────────────┴──→ REJECTED/CANCELLED/EXPIRED
```

실제 허용 전이는 `ApplicationStatus`와 `WorkflowStateTransitionTest`가 기준입니다. Controller에서 임의 상태를 받더라도 service가 현재 상태와 요청자의 역할을 다시 확인합니다.

## 2. 출결 변경 요청 상태

```text
PENDING ──→ APPROVED
    └──────→ REJECTED
```

승인 전에는 원래 출결을 변경하지 않습니다. 승인 시 대상 원생·날짜·요청자 관계를 다시 검증하고, idempotency key로 동일 요청이 두 번 반영되지 않게 합니다.

## 3. Outbox 상태

```text
PENDING → PROCESSING → DELIVERED
                    ├→ PENDING(retry)
                    └→ DEAD_LETTER
```

실패가 재시도 가능하면 다음 실행 시각을 계산해 `PENDING`으로 예약하고, 최대 시도 횟수를 넘으면 `DEAD_LETTER`로 격리합니다. 코드에 별도의 `FAILED` enum은 두지 않았습니다. 외부 provider의 지연이나 장애가 업무 transaction을 실패시키지 않도록 전달을 분리하고, dead-letter는 원장 전용 운영 화면에서 조회하고 명시적으로 retry합니다.

## 4. 권한 판정 순서

| 계층 | 질문 | 예시 |
| --- | --- | --- |
| URL 규칙 | 이 역할이 이 화면/API에 들어갈 수 있는가? | `/notification-outbox`는 원장만 |
| Controller annotation | 메서드 진입 역할이 맞는가? | `@PreAuthorize` |
| Service policy | 이 사용자가 대상 tenant·원생·반과 관계가 있는가? | `AccessPolicyService` |
| Repository query | 조회 조건에 tenant/삭제 조건이 빠지지 않았는가? | `kindergarten_id`, `deleted_at` |
| 테스트 | 다른 역할·다른 tenant가 실패하는가? | API/Page access integration test |

한 계층만 믿지 않는 이유는 URL 권한 우회, IDOR, service 직접 호출, query 누락을 각각 다른 층에서 막기 위해서입니다.

## 5. 동시성·멱등성 답변

면접에서 “동시에 두 명이 승인하면 어떻게 하나요?”라는 질문에는 다음처럼 답합니다.

> 상태 전이는 현재 상태를 다시 확인하는 service transaction 안에서 수행하고, 허용되지 않은 현재 상태에서는 BusinessException을 반환합니다. 학부모 출결 변경 요청은 requester별 idempotency key에 unique 제약을 두어 재시도 요청이 중복 저장되지 않게 했습니다. Outbox worker는 처리 중인 행을 선점해 같은 메시지가 동시에 전달되지 않도록 설계했습니다. 다만 실제 운영 DB의 isolation·부하 조건은 배포 후 별도 측정 대상입니다.

## 6. tenant 격리 답변

> 로그인한 사용자의 역할만으로 데이터 접근을 허용하지 않고, 유치원 소속과 원생·반 관계를 함께 검증합니다. Controller의 URL 권한, service의 `AccessPolicyService`, repository의 tenant 조건, 교차 tenant 통합 테스트를 겹쳐 적용했습니다. 그래서 `/kids/{id}`처럼 ID를 바꿔 요청하는 경우도 대상 자원이 다른 유치원에 속하면 거절됩니다.
