# 설계 의사결정 기록

각 결정은 사용한 기술보다 문제, 버린 대안, trade-off와 전환 조건을 설명하기 위한 자료입니다.

## 1. 모놀리식으로 유지

- 문제: 입학·출결·알림·감사가 같은 tenant transaction과 권한 정책을 공유합니다.
- 선택: Spring Boot 안에서 domain package 경계를 유지합니다.
- 버린 대안: 처음부터 microservice로 분리합니다.
- 이유: 서비스 간 transaction, 권한 전파, retry, 배포 복잡도가 문제의 본질보다 커집니다.
- 전환 신호: 알림 worker 독립 scaling이나 audit read traffic이 실제 병목으로 측정될 때입니다.

## 2. JWT HTTP-only cookie와 Redis session

- 문제: SSR 브라우저에서 token을 JavaScript에 노출하지 않으면서 refresh 철회가 필요합니다.
- 선택: access/refresh cookie와 Redis TTL·active session registry입니다.
- 버린 대안: localStorage token, DB-only session입니다.
- trade-off: cookie CSRF 방어가 추가되고 Redis 장애 정책이 필요합니다.
- 근거: `SecurityConfig`, `JwtFilter`, `AuthSessionRegistryService`.

## 3. URL 권한과 service policy 중첩

- 문제: `ROLE_PRINCIPAL`만으로는 특정 유치원·원생·반의 소유 범위를 알 수 없습니다.
- 선택: SecurityConfig/PreAuthorize + `AccessPolicyService` + query tenant 조건입니다.
- 버린 대안: Controller URL role check만 적용하는 것입니다.
- trade-off: 검증이 중복될 수 있어 공통 policy와 도메인별 재검증을 함께 둡니다.

## 4. Outbox와 channel adapter

- 문제: 외부 email/push/webhook 실패가 핵심 업무 transaction을 실패시키면 안 됩니다.
- 선택: DB Outbox, scheduled worker, sender registry, retry/backoff/dead-letter입니다.
- 버린 대안: 업무 service의 동기 HTTP 호출, Kafka 선도입입니다.
- 이유: 현재는 durable delivery 상태와 운영 retry가 먼저 필요하고 broker를 정당화할 backlog 증거가 없습니다.
- trade-off: claim, stale reclaim, 중복 전달, 보관 정책을 관리해야 합니다.

## 5. 출결 요청 멱등 키를 DB까지 내림

- 문제: 브라우저 재시도로 같은 변경 요청이 중복 생성될 수 있습니다.
- 선택: `Idempotency-Key`를 requester와 함께 저장하고 unique 제약을 둡니다.
- 버린 대안: 메모리 map, 시간 기반 중복 검사입니다.
- 이유: 재시작·다중 인스턴스에서도 보장하려면 DB 경계가 필요합니다.
- trade-off: key 재사용 시 같은 요청 의미를 유지해야 하고 보관 기간 정책이 필요합니다.

## 6. OSIV OFF와 DTO 조회

- 문제: View에서 lazy loading이 발생하면 query가 숨고 transaction 경계가 흐려집니다.
- 선택: OSIV OFF, service에서 DTO/projection 구성입니다.
- 버린 대안: OSIV ON으로 화면 오류를 늦추는 것입니다.
- trade-off: fetch/query 설계가 더 필요하고 화면별 DTO가 늘어납니다.

## 7. QueryDSL은 복잡한 조회에만 사용

단순 CRUD는 Spring Data 메서드로 두고, 역할·tenant·상태·검색어·기간이 결합되는 운영 조회는 QueryDSL/custom repository로 분리합니다. 전 도메인을 QueryDSL로 통일하지 않은 이유는 Simple is Best 원칙과 유지보수 비용 때문입니다.

## 8. local/demo/prod fail-closed

demo의 seed·Swagger·app-port Prometheus와 prod의 안전 기본값은 다릅니다. `StartupSafetyValidator`로 seed·Swagger·약한 secret·비HTTPS CORS가 prod에서 켜지지 않게 합니다. 편의 기본값을 모든 환경에 공유하는 대안은 거부했습니다.

## 답변 구조

```text
문제 → 선택 → 버린 대안 → 선택 이유 → trade-off → 현재 검증 → 전환 신호
```
