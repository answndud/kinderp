# KinderP 보안 점검 보고서

점검일: 2026-08-20  
범위: 저장소의 현재 Git 추적 파일·전체 Git 이력·Spring Boot/Thymeleaf 코드·Flyway·Docker/CI·운영 문서. 실제 VPS, GitHub Secrets, OAuth 콘솔, DB GRANT, object storage는 저장소 밖이므로 해당 항목은 `WARN`으로 구분했다.

## 판정 기준과 수행 근거

- Secret: `git ls-files`, `.gitignore`, 전체 reachable Git blob/patch에서 AWS·Google·GitHub·OpenAI·Slack 형식과 PEM private key 패턴을 검색했다. 알려진 형식의 실제 값은 발견되지 않았다.
- 코드: `rg`로 컨트롤러, 입력 검증, 파일 업로드, 동적 SQL/명령 실행, HTML 삽입, 외부 HTTP 호출을 전수 검색하고 인증·인가 경로를 수동 추적했다.
- 의존성: `npm audit --omit=dev --package-lock-only --json`은 production 의존성 취약점 0건을 반환했다. Java runtime 의존성은 OWASP Dependency-Check `dependencyCheckAnalyze` 게이트(CVSS 7.0 이상 실패)와 `runtimeClasspath` 해석으로 관리한다.
- 실행 검증: `npm run security:inline-handlers`, `npm run security:view-errors`, `npm run security:product-time` 및 `./gradlew test --tests 'com.kinderp.api.AuthApiIntegrationTest' --tests 'com.kinderp.integration.ManagementSurfaceOptInIntegrationTest' --tests 'com.kinderp.integration.PageAccessIntegrationTest'`가 통과했다.

## Medium Risk

`[WARN] 백업 데이터도 접근제어 또는 암호화되어 있는가`

- 위험도: Medium
- 위치: `docs/guides/netcup-deployment.md:93`, `deploy/encrypt-backup.sh:1`
- 문제: `age` 암호화 절차는 존재하지만 recipient/private key 보관 위치와 외부 bucket ACL은 저장소 밖이라 실제 적용 여부를 증명할 수 없다.
- 공격 시나리오: 평문 dump 또는 복호화 키가 같은 서버/공개 bucket에 남으면 백업 탈취로 개인정보가 노출될 수 있다.
- 권장 수정: age recipient를 조직 키 관리 체계에 등록하고, backup object storage를 private·versioning·immutable retention으로 설정한다.
- 검증 방법: 권한 없는 계정의 object 읽기 실패와 authorized restore 성공을 기록한다.

`[WARN] Secret 유출·DB 침해 발생 시 폐기해야 할 Key와 대응 절차를 식별할 수 있는가`

- 위험도: Medium
- 위치: `docs/guides/env-contract.md:77`, `docs/guides/risk-response.md:1`
- 문제: 필수 secret 목록은 있으나 유출 사고 시 JWT/OAuth/DB/Redis/SMTP/webhook/GHCR 자격증명의 폐기 순서, 세션 무효화, 증적 보존 및 담당자 절차가 없다.
- 공격 시나리오: 유출 대응이 늦거나 JWT secret 교체 후 기존 세션을 즉시 무효화하지 못해 공격자가 계속 접근할 수 있다.
- 권장 수정: incident runbook에 자격증명 inventory·owner·rotation 명령·JWT 전체 세션 revoke·OAuth redirect/secret 교체·DB 비밀번호 교체·통지/포렌식 단계를 추가한다.
- 검증 방법: staging tabletop exercise에서 테스트 secret 유출 시나리오를 수행하고, 교체 후 이전 JWT/DB 비밀번호/webhook 서명이 실패하는지 확인한다.

## Low Risk / Improvements

`[WARN] 하드코딩된 Secret이 없는가`

- 위험도: Low
- 위치: `src/main/resources/application-local.yml:10`, `src/main/resources/application-local.yml:74`, `docker/.env.example:10`
- 문제: local 전용 DB/JWT fallback과 Docker 예제의 `root1234`, `erp1234`, `admin1234!`가 저장소에 고정돼 있다. prod는 환경 변수와 `StartupSafetyValidator`로 차단한다.
- 공격 시나리오: 개발자가 이 예제 값을 인터넷 노출 개발 환경이나 운영 환경에 재사용하면 알려진 자격증명으로 접근될 수 있다.
- 권장 수정: 예제에는 무작위 생성 명령 또는 placeholder를 사용하고, local compose 시작 시 고유 secret을 생성하도록 한다. prod 차단 테스트는 유지한다.
- 검증 방법: 예제 값을 그대로 둔 prod profile이 부팅 실패하고, local 생성값이 `.gitignore`된 파일에만 저장되는지 확인한다.

`[WARN] API Key에 최소 권한·만료·Rotation 정책을 적용할 수 있는가`

- 위험도: Low
- 위치: `docs/guides/env-contract.md:77`, `deploy/.env.prod.example:10`
- 문제: 필요한 secret 변수는 정의되어 있지만 OAuth/webhook/GHCR key의 scope·만료·정기 rotation 주기와 소유자가 정책으로 고정돼 있지 않다.
- 공격 시나리오: 장기·광범위 key가 유출되면 피해 범위와 유효 기간이 불필요하게 커진다.
- 권장 수정: key inventory에 용도·최소 scope·owner·만료일·rotation 주기를 기록하고, GitHub fine-grained token 및 provider별 최소 권한을 적용한다.
- 검증 방법: inventory의 만료/rotation 알림과 expired key의 호출 실패를 staging에서 확인한다.

`[WARN] 사용하지 않는 패키지가 제거되어 있는가`

- 위험도: Low
- 위치: `build.gradle:1`, `package.json:1`
- 문제: 선언 의존성은 버전 관리되지만 unused-dependency 분석을 release gate로 실행하는 설정은 없다.
- 공격 시나리오: 불필요한 라이브러리가 공격 표면과 이후 취약점 대응 비용을 증가시킨다.
- 권장 수정: Java와 Node 각각의 unused dependency 검사를 CI의 advisory check로 추가하고, 의도적 runtime/reflection 사용은 allowlist로 관리한다.
- 검증 방법: 사용되지 않는 테스트 의존성 fixture를 넣었을 때 report가 검출하는지 확인한다.

`[WARN] Lock File이 존재하고 의존성 버전이 통제되고 있는가`

- 위험도: Low
- 위치: `package-lock.json:1`, `build.gradle:1`
- 문제: Node는 `package-lock.json`이 있으나 Gradle dependency locking 파일이 없어 Java transitive 해석 결과를 재현 가능한 lock으로 고정하지 않는다.
- 공격 시나리오: 저장소를 나중에 다시 빌드할 때 BOM/동적 전이 해석 차이로 의도치 않은 버전이 선택될 수 있다.
- 권장 수정: Gradle dependency locking을 활성화하고 runtime/test configuration lock을 커밋한다.
- 검증 방법: 깨끗한 환경에서 `./gradlew dependencies --write-locks` 후 lock 변경이 없는지 CI에서 검사한다.

`[WARN] 비정상적인 API 호출 증가를 감지할 수 있는가`

- 위험도: Low
- 위치: `docker/monitoring/prometheus/alerts.yml:13`, `src/main/java/com/kinderp/domain/authaudit/service/AuthAnomalyAlertService.java:33`
- 문제: readiness, 5xx 비율, dead-letter와 반복 로그인 실패 알림은 있으나 4xx/429 급증, endpoint별 호출량, 인증 성공 후 abuse 급증 alert는 없다.
- 공격 시나리오: 공격자가 정상 응답 또는 4xx를 대량 발생시켜도 현재 alert rule만으로는 빠르게 식별하기 어렵다.
- 권장 수정: endpoint/상태군별 request rate와 401/403/429 급증 alert, tenant별 anomaly dashboard를 추가한다.
- 검증 방법: Prometheus rule test 또는 staging 부하에서 임계치 초과 시 Alertmanager 수신을 확인한다.

`[WARN] 외부 API/클라우드 비용 급증 알림이 설정 가능한가`

- 위험도: Low
- 위치: `docker/monitoring/prometheus/alerts.yml:1`
- 문제: 비용·전송량 budget alert와 cloud billing alert 설정은 저장소에 없다.
- 공격 시나리오: webhook/email/cloud 리소스 비용이 비정상 증가해도 청구 시점까지 발견이 지연될 수 있다.
- 권장 수정: provider usage/billing metric 또는 일일 outbox 전송량을 alert rule에 연결하고, cloud provider budget alert를 운영 계정에서 설정한다.
- 검증 방법: 테스트 metric 또는 sandbox budget으로 알림 수신을 확인한다.
