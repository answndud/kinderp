# 외부 API 호출 Rate Limit 개선 완료

기준일: 2026-08-21

AI·결제 API는 현재 구현되어 있지 않으며, 외부 비용이 발생할 수 있는 알림 webhook/email 호출은 서버 outbox worker가 수행한다. 사용자 입력으로 알림을 생성하는 API에는 다음 제한을 적용했다.

- `POST /api/v1/notifications` 요청을 Redis에서 사용자 ID와 신뢰된 클라이언트 IP별로 동시에 제한
- 기본값: 사용자 30회/1분, IP 100회/1분
- 초과 시 알림 outbox에 enqueue하지 않고 HTTP 429와 `Retry-After: 60` 반환
- `NOTIFICATION_RATE_LIMIT_WINDOW`, `NOTIFICATION_RATE_LIMIT_USER`, `NOTIFICATION_RATE_LIMIT_IP`로 운영 환경별 조정 가능
- `NotificationApiIntegrationTest`에서 사용자별 제한 초과와 429 응답을 검증

검증 명령:

```bash
./gradlew compileJava compileTestJava
./gradlew fastTest
npm run docs:links
```

## Resource Limit 개선

`server.request-limits`와 Tomcat connector 설정을 추가해 요청 자원 상한을 명시했다.

- HTTP request header 최대 16KB
- 일반 요청 body 및 form POST 최대 1MB
- header 최대 100개, parameter 최대 100개
- Content-Length가 1MB를 초과하거나 filter에서 header/parameter 수를 초과하면 애플리케이션 진입 전에 HTTP 413으로 차단
- 목록 API page size는 공통 최대 100개, 감사 로그 CSV export는 최대 10,000행으로 제한
- AI API와 LLM token 사용량 제한은 현재 적용 대상 기능이 없어 N/A로 기록
- `RequestLimitFilterTest`에서 oversized body와 parameter 초과 차단을 검증

## Dependency CVE 검사 개선

- `org.owasp.dependencycheck` Gradle plugin `12.2.2`를 추가하고 CVSS 7.0 이상이면 빌드를 실패하도록 구성
- `backend-quality` workflow에서 `dependencyCheckAnalyze`를 실행하며 `NVD_API_KEY` secret을 선택적으로 사용
- CI에서 `npm audit --omit=dev --audit-level=high`를 실행하고 Dependabot이 Gradle/npm/GitHub Actions 업데이트 PR을 매주 생성
- 로컬 `npm audit --omit=dev --package-lock-only --json` 결과는 production 취약점 0건
- Java Dependency-Check는 NVD API key 없이 갱신을 시도했으나 현재 실행 환경에서 API 응답이 지연되어 완료 증적을 생성하지 못했다. CI에서는 `NVD_API_KEY`를 등록한 뒤 `dependencyCheckAnalyze` 결과를 release 증적으로 보관해야 한다.

## DB 및 중요 데이터 백업 정책 개선

- `scripts/backup-netcup.sh`가 MySQL·Redis container를 함께 백업하고 SHA-256 checksum을 생성
- `deploy/systemd/kinderp-backup.timer`가 매일 03:30에 실행되며 `Persistent=true`로 재부팅 후 누락 실행을 보완
- `BACKUP_RETENTION_DAYS` 기본값 14일로 오래된 local backup을 정리하고, staging 실패 시 partial directory를 삭제
- `/opt/kinderp/secrets/backup.env`에 backup 자격증명을 별도 보관하며 systemd 서비스에서만 읽도록 문서화
- checksum 검증과 disposable restore 절차는 기존 `scripts/verify-production-backup.sh`, `scripts/restore-production-backup.sh`를 사용
- 외부 암호화 object storage 복제와 접근제어는 다음 Medium Risk 항목에서 별도 적용

## 백업 접근제어·암호화 개선

- `scripts/backup-and-publish-netcup.sh`가 백업 완료 후 `publish-encrypted-backup.sh`를 호출
- `age` recipient로 tar archive를 암호화하고, 별도 SSH 저장소의 전용 계정·고정 known_hosts·StrictHostKeyChecking을 사용
- 원격 백업 디렉터리는 `700`, 암호화 파일과 checksum은 `600`으로 설정하며 기존 파일 덮어쓰기를 거부
- 원격 수신 후 checksum을 다시 검증해 전송 중 변조를 확인
- 원격 private key와 known_hosts는 `/opt/kinderp/secrets` 외부 secret 파일에 보관하며 Git에 포함하지 않음

## Secret 유출·DB 침해 대응 개선

- `docs/guides/secret-incident-response.md`에 JWT/OAuth/DB/Redis/SMTP/webhook/GHCR/백업 자격증명 inventory와 책임·rotation·검증 순서를 추가
- `scripts/revoke-production-sessions.sh`는 `--confirm-all-sessions` 없이는 실행되지 않고 Redis `refresh:*` 키만 전체 폐기
- Contain → Revoke → 세션 무효화 → 인프라 rotation → disposable restore/smoke → 통지·회고 순서를 고정
- 실제 provider revoke와 운영 tabletop 실행은 외부 자격증명·담당자가 연결된 뒤 증적을 보관해야 함
