# TownPet과 KinderP의 차별화

두 프로젝트 모두 Java/Spring 기반의 모놀리식 백엔드 포트폴리오이지만, 같은 말을 반복하지 않도록 문제의 축을 분리해 설명합니다.

## 1. 한눈에 보는 차이

| 구분 | TownPet | KinderP |
| --- | --- | --- |
| 도메인 | 반려동물 커뮤니티·마켓·돌봄 | 유치원 내부 운영 ERP |
| 대표 사용자 | 일반 회원·운영자 | 원장·교사·학부모 |
| 핵심 문제 | 공개 커뮤니티 데이터를 새 구조로 전환하고 피드·검색·페이지네이션을 안정화 | 같은 tenant의 업무 데이터를 역할별로 처리하고 승인·정정·전달 실패를 통제 |
| 대표 설계 | 데이터 마이그레이션, 공개 피드, 검색·페이지네이션, PostgreSQL/Flyway | 접근 정책, 상태 머신, 멱등성, Outbox, 감사 로그, Redis session |
| 성능 질문 | 피드 조회·검색·대규모 읽기 경로 | 대시보드·알림장 query count와 cache hit |
| 운영 질문 | 릴리스·마이그레이션·복구·피드 용량 | 권한 사고·상태 충돌·알림 실패·운영 조사 |
| 보여주는 역량 | 레거시 전환과 읽기 확장 | 업무 정합성과 실패를 운영 가능한 상태로 만드는 능력 |

## 2. 면접에서 연결하는 문장

> TownPet에서는 기존 데이터를 새 서비스 구조로 옮기고 공개 읽기 트래픽을 안정화하는 문제를 다뤘습니다. KinderP에서는 데이터가 공개되면 안 되는 내부 운영 환경에서 원장·교사·학부모의 권한과 상태 전이를 닫는 문제를 다뤘습니다. 전자는 시스템 전환과 읽기 확장, 후자는 업무 정합성과 운영 실패 통제가 중심입니다.

## 3. TownPet과 겹치지 않는 대표 사례

### 사례 A: 교차 tenant 접근 차단

KinderP에서는 `/kids/{id}` 같은 ID가 있어도 그 원생이 로그인 사용자의 유치원 또는 부모 관계에 속하는지 service에서 확인합니다. 이는 공개 커뮤니티의 리소스 조회와 다른 내부 업무 보안 문제입니다.

### 사례 B: 출결 요청 멱등성

학부모가 네트워크 재시도로 같은 출결 변경을 여러 번 보내도 requester별 멱등 키와 DB 제약으로 한 번만 반영합니다. 커뮤니티 글 작성과 달리 승인 전후 상태와 업무 효과를 함께 보호해야 합니다.

### 사례 C: Outbox 운영면

알림 전달 실패를 단순 로그로 끝내지 않고 상태·채널·검색·dead-letter·retry 화면으로 만들었습니다. 외부 provider가 일시적으로 실패해도 핵심 업무 transaction을 되돌리지 않는 운영 설계입니다.

## 4. 공통점도 정직하게 설명하기

- 둘 다 현재 규모에서는 모놀리식 구조가 합리적이라고 판단했습니다.
- 둘 다 Flyway와 자동화된 검증을 통해 변경을 재현 가능하게 했습니다.
- 둘 다 실제 운영 데이터와 외부 클라우드 사용을 과장하지 않습니다.
- 공통 기술을 사용했지만, 문제 정의와 성능 측정 대상이 다릅니다.

## 5. 지원 직무 연결

토스뱅크 Server Developer 관점에서는 다음 역량으로 연결합니다.

| 요구 역량 | 증거 |
| --- | --- |
| 요구사항을 데이터/API로 구체화 | 입학·출결·Outbox 상태 전이와 API 계약 |
| 확장 가능한 서버 설계 | domain 모듈 경계, QueryDSL 조회, Redis cache/session |
| 성능 최적화 | Notepad 22→5 query, Dashboard cache hit 5→0 query |
| 보안 감각 | cookie JWT, rate limit, CSRF/CSP, tenant 정책, prod safety |
| 자동화·운영 | CI quick/heavy, readiness, backup/restore, deploy SHA, audit |
| 한계 인식 | 미배포·provider 미연동 범위와 다음 검증 계획 공개 |
